# Machine Fault Detection System

An end-to-end Machine Learning application for detecting and classifying machine failures using the **AI4I 2020 Predictive Maintenance Dataset**.

The system trains and evaluates three different machine learning models—**Random Forest, XGBoost, and LightGBM**—and combines their prediction probabilities through a **soft-voting ensemble approach** to produce a final machine health status, fault classification, and confidence score.

The project also includes a web-based frontend and Flask backend, demonstrating communication between the frontend, REST API, preprocessing pipeline, trained machine learning models, and ensemble prediction logic.

---

## 🚀 Project Overview

Unexpected machine failures can result in production downtime, maintenance costs, and reduced operational efficiency. Predictive maintenance systems use machine operating parameters to identify potential failures before they cause significant disruption.

This project implements a machine fault detection system that accepts machine operating parameters and predicts whether the machine is:

* **HEALTHY**
* **FAULT DETECTED**

If a fault is detected, the system further identifies the specific failure category.

The application uses three independently trained machine learning models:

1. **Random Forest Classifier**
2. **XGBoost Classifier**
3. **LightGBM Classifier**

The prediction probabilities generated by the three models are averaged to produce an ensemble prediction.

## 📊 Dataset

The project uses the **AI4I 2020 Predictive Maintenance Dataset**, which contains machine operating parameters and corresponding machine failure information.

### Input Features

The prediction system uses the following six features:

| Feature                   | Data Type | Description                   |
| ------------------------- | --------- | ----------------------------- |
| `Type`                    | String    | Machine/product type          |
| `Air temperature [K]`     | Float     | Air temperature in Kelvin     |
| `Process temperature [K]` | Float     | Process temperature in Kelvin |
| `Rotational speed [rpm]`  | Integer   | Machine rotational speed      |
| `Torque [Nm]`             | Float     | Machine torque                |
| `Tool wear [min]`         | Integer   | Tool usage/wear time          |

### Target Classes

The target variable represents the type of machine failure.

| Class | Label                          |
| ----: | ------------------------------ |
|   `0` | No Failure                     |
|   `1` | Tool Wear Failure (TWF)        |
|   `2` | Heat Dissipation Failure (HDF) |
|   `3` | Power Failure (PWF)            |
|   `4` | Overstrain Failure (OSF)       |
|   `5` | Random Failure (RNF)           |
|   `6` | General Machine Failure        |

The numeric class generated by the machine learning model is converted into a meaningful human-readable label before being presented to the user.

## 🤖 Machine Learning Models

Three classification algorithms were trained and used independently:

### 1. Random Forest

Random Forest is an ensemble learning algorithm that combines multiple decision trees to improve classification performance and generalization.

### 2. XGBoost

XGBoost is a gradient boosting algorithm that builds sequential decision trees and is widely used for structured/tabular machine learning problems.

### 3. LightGBM

LightGBM is a gradient boosting framework designed for efficient and high-performance learning on tabular datasets.

Using three different models allows the system to compare their individual predictions and combine their probability estimates into a final ensemble prediction.

---

## 🔄 Ensemble Prediction

Instead of relying on only one model, the application obtains prediction probabilities from all three models.

The probability vectors are combined by calculating their average:

```python
ensemble_probability = (
    rf_probability +
    lgbm_probability +
    xgb_probability
) / 3
```

The class with the highest averaged probability is selected as the final prediction:

```python
final_index = int(np.argmax(ensemble_probability))
```

This approach can be described as **soft voting / probability averaging**.

### Ensemble Flow

```text
                    Machine Parameters
                           │
             ┌─────────────┼─────────────┐
             │             │             │
             ▼             ▼             ▼
        Random Forest    XGBoost      LightGBM
             │             │             │
             ▼             ▼             ▼
       Class Probabilities from Each Model
             │             │             │
             └─────────────┼─────────────┘
                           ▼
                 Average Probabilities
                           │
                           ▼
                  Highest Probability
                           │
                           ▼
                  Final Class Prediction
```

## 📈 Final Prediction Logic

The final ensemble class is mapped to a meaningful failure description:

```python
class_names = {
    0: "No Failure",
    1: "Tool Wear Failure (TWF)",
    2: "Heat Dissipation Failure (HDF)",
    3: "Power Failure (PWF)",
    4: "Overstrain Failure (OSF)",
    5: "Random Failure (RNF)",
    6: "General Machine Failure"
}
```

The system then determines the overall machine status:

```python
machine_failure = "HEALTHY" if final_index == 0 else "FAULT DETECTED"
```

Therefore:

* Class `0` → **HEALTHY**
* Classes `1–6` → **FAULT DETECTED**

The final prediction is then converted from a numeric class into its descriptive label:

```python
final_prediction = class_names[final_index]
```

---

## 🎯 Confidence Score

The ensemble probability corresponding to the selected class is used as the confidence score.

```python
confidence = f"{ensemble_probability[final_index] * 100:.2f}"
```

For example, the API can return a prediction conceptually represented as:

```json
{
    "status": "FAULT DETECTED",
    "prediction": "Heat Dissipation Failure (HDF)",
    "confidence": "91.43"
}
```

The frontend can then display the prediction in a user-friendly format rather than exposing raw numeric model output.

> **Note:** The confidence value represents the ensemble's averaged predicted probability for the selected class; it should not automatically be interpreted as a formally calibrated probability of correctness.

## 💾 Model Export

After training, the trained machine learning models were exported using `joblib`.

This allows the application to load the trained models during prediction without retraining them every time a user makes a request.

Conceptually:

```text
Training
   ↓
Train Model
   ↓
Evaluate Model
   ↓
Export using joblib
   ↓
Saved Model File
   ↓
Load Model in Flask
   ↓
Make Prediction
```

The deployed application therefore performs **inference**, rather than training the models whenever a prediction request is received.

## 🔌 Frontend–Backend Communication

The frontend communicates with the Flask backend through HTTP requests using JavaScript's `fetch` API and `async`/`await`.

The frontend collects the six machine parameters and sends them to the prediction API in JSON format.

Conceptually:

```json
{
    "Type": "M",
    "Air temperature [K]": 298.5,
    "Process temperature [K]": 308.2,
    "Rotational speed [rpm]": 1550,
    "Torque [Nm]": 42.5,
    "Tool wear [min]": 120
}
```

A simplified version of the frontend request flow is:

```javascript
async function getPrediction(machineData) {
    const response = await fetch("BACKEND_API_URL", {
        method: "POST",
        headers: {
            "Content-Type": "application/json"
        },
        body: JSON.stringify(machineData)
    });

    return await response.json();
}
```

The Flask backend receives the request, passes the data through the prediction process, and returns the final result as JSON.

```text
Vanilla JavaScript
  │
  │ POST + JSON using fetch/async/await
  ▼
Flask API
  │
  ├── Validate Input
  │
  ├── Prepare Data
  │
  ├── Random Forest Prediction
  │
  ├── XGBoost Prediction
  │
  ├── LightGBM Prediction
  │
  ├── Ensemble Probability
  │
  └── Final Prediction
  │
  ▼
JSON Response
  │
  ▼
JavaScript updates the page
```

## 🧠 Handling Class Imbalance

Machine failure datasets can contain significantly fewer examples of some failure categories compared with the normal/no-failure class.

This makes class imbalance an important consideration during model development.

The project therefore considers the individual failure classes rather than evaluating the system only through overall accuracy.

Model evaluation should consider metrics such as:

* Precision
* Recall
* F1-score
* Macro average
* Confusion matrix

This is particularly important because a high overall accuracy can be misleading when the majority class dominates the dataset.

### Render Free-Tier Notice

The backend uses Render's free tier. After approximately 15 minutes without activity, the service may enter a sleeping state. When a new request arrives after the service has gone to sleep, the backend may require additional time to wake up.

As a result:

* The first request after inactivity may be slower.
* The frontend may appear to wait while the backend starts.
* Later requests should generally respond faster once the service is awake.
* This behavior is a limitation of the hosting plan rather than the prediction logic.
